1 · The Mental Model (the receptionist)

Your API is a receptionist behind a phone line. The client calls; the receptionist consults the filing cabinet (database); the receptionist answers.

Client (browser / curl) ──request──► SERVER (FastAPI) ──query──► DATABASE (SQLite file) Client ◄──response── SERVER ◄──rows── DATABASE
  • Server = a program listening on a port (9000). Starts with uvicorn, dies when you close it.
  • Endpoint = one page in the rulebook = one @app.xxx function.
  • Request = method + URL + optional body.   Response = status code + body.
💡 The database file is innocent. It only stores truth. Lies live in the translation layer (your code). Most bugs are translators, not data.

3 · Types Are Law (the quote-ghost cure)

In Week 1 the ghost "row[2]" slipped through because nothing knew price was a number. Now the class declares it, and the type system enforces it on the way in, in storage, and on the way out.

class Product(SQLModel, table=True):     # the LAW
    __tablename__ = "products"           # tell the ORM the table's TRUE name
    id:    int | None = Field(default=None, primary_key=True)
    name:  str                            # text required
    price: int                            # NUMBER required — quotes forbidden
You sendWhat happens
{"name":"Mouse","price":500}✅ 200, stored as integer
{"name":"Mouse","price":"500"}🛡️ 422 — shield blocks the quoted string
⚕️ You didn’t patch the hole; you removed the ground it stood on. The Week-1 bug is now physically impossible to write.

5 · SQL Sentences You Must Memorize (the grammar)

SELECT * FROM products WHERE id = 1;                          -- read
INSERT INTO products (name, price) VALUES ('Mouse', 500);     -- create
UPDATE products SET name='X', price=9 WHERE id=1;             -- update
DELETE FROM products WHERE id = 1;            -- destroy  (FROM is NOT optional!)

The comma landmine

cursor.execute(sql, (product_id))     # ❌ (5) is just the int 5
cursor.execute(sql, (product_id,))    # ✅ (5,) is a TUPLE — the comma IS the tuple
⚠️ Parentheses are decoration. The comma makes the tuple. One character, one whole bug class.
📏 rowcount = the honesty meter: after UPDATE/DELETE it tells how many rows actually changed. 0 ⇒ the id never existed ⇒ raise 404. Never trust “success” without checking the meter.

6 · The Debugging Doctrine (your superpower)

  • Writes claim. Reads prove. After every POST/PUT/DELETE, run GET and look. The server’s “updated!” is a promise; the GET is the evidence.
  • Descend the layers when the UI lies: browser → server logs → curl → the file itself. (This is how you caught the twin-database ghost.)
  • Read the traceback bottom-up. The last line names the error; the line above names your file and line number. The log is a free teacher that never sleeps.
  • Timestamps are security cameras. Compare the response’s date: header to your clock. Old header = you’re reading history, not truth (stale Swagger panel).
  • Predict before you run. Say out loud what you expect, then execute. Wrong prediction = the exact spot your mental model needs fixing. The #1 engineer skill.
  • Run before review. Test your own code; bring the error + your one fix attempt. Don’t hand over untested code to debug for you.

⭐ The Ten Golden Rules (if you remember nothing else)

  1. The database is innocent; the translator lies.
  2. Types are law — declare them and the bug can’t be written.
  3. Writes claim; reads prove.
  4. The comma makes the tuple. (5,)
  5. DELETE FROM — grammar is strict.
  6. Relative paths obey where you stand, not where the file is.
  7. One Python per project (py -3.10 -m ...); venv is the cure (coming next).
  8. Read the traceback bottom-up; the log never sleeps.
  9. Predict before you run; run before you review.
  10. Commit the why, ignore the junk, never track your data.
